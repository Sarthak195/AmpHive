### 1. [HIGH] Cross-tenant billing inflation: telemetry payload plug_id feeds the live TelemetryStore before the ownership check, and finalize bills against it

- **Location:** `backend/services/mqtt/telemetry.py:214`  
- **Surface / category:** mqtt / cross-tenant-billing-tampering  
- **What:** In _handle_gateway_telemetry, the inbound frame's plug_id and energy value are pushed into the process-wide singleton TelemetryStore (telemetry.py:214-232, `telemetry_store.update(plug_id, watts, current, kwh, ...)`) with NO verification that plug_id belongs to the publishing gateway. The gateway_id used for routing comes from the topic (mqtt_manager.py:222), and the broker ACL (`pattern readwrite amphive/gateways/%u/#`, deploy-relay.sh:228) only scopes the TOPIC a client may publish to — it does not constrain the plug_id inside the JSON body. The ownership guard that the code relies on (`plug.gateway_id != gateway_id`, telemetry.py:399-408, whose own docstring says it exists so 'a compromised gateway could otherwise attribute energy/billing to another tenant's plug') lives only in the async _persist_telemetry DB path. It correctly blocks the DB write, but it runs AFTER and independently of the synchronous store feed. The poisoned store value is then trusted for real money: finalize_charging_session reads `latest = state.telemetry_store.get_latest(plug.id)` and bills `final_energy = max(live_energy, persisted_energy)` -> `final_cost = session_cost(session, final_energy)` (session_lifecycle.py:198-207), debiting the driver's wallet (session_lifecycle.py:246-251). The kwh bound check (MAX_PLAUSIBLE_KWH=1000, telemetry.py:146) sits before the store feed, so an attacker can pin a victim plug's live energy up to 1000 kWh. Because the persisted energy is only ever written through the guarded path, the attacker-controlled live value wins the max() whenever it is higher. state.telemetry_store and the manager's store are the same singleton (state.py:23, telemetry.py:69-74), and end_session cleanup happens only after billing (session_lifecycle.py:328), so the poisoned snapshot is live at finalize time.  
- **Exploit:** Attacker is any tenant who operates one legitimately-provisioned gateway or software agent (valid MQTT creds for its own subtree amphive/gateways/attacker-gw/#). Victim is another tenant whose driver has an ACTIVE session on plug_id=V (small sequential int, easily guessed/enumerated). The attacker publishes to its OWN allowed topic `amphive/gateways/attacker-gw/telemetry` a body `{"plug_id": V, "watts": 15000, "kwh": 1000, "status": "occupied", "session_id": ""}`, repeating a few times/sec to stay the latest writer. The backend routes it as gateway_id=attacker-gw, and telemetry_store.update(V, energy_kwh=1000, ...) poisons the shared store for the victim's plug (the DB-persist path drops it on the ownership check, so nothing looks wrong server-side). The victim driver simultaneously sees a spiking cost on their live monitor. When the victim's session finalizes (driver stop, balance/limit auto-stop, or the reaper), finalize reads live_energy=1000, bills session_cost(session, 1000) and debits the driver's wallet up to min(final_cost, hold) (or the whole wallet balance for a legacy no-hold session), and stamps the session/receipt with the fabricated 1000 kWh. Net effect: one tenant can inflate the electricity bill and drain the wallet of another tenant's drivers, and corrupt their billing records, without ever touching the victim's own topics.  
- **Fix:** Apply the same ownership check to the live store feed that already guards the DB write. Simplest correct fix: remove the unconditional telemetry_store.update(...) block from _handle_gateway_telemetry (telemetry.py:214-232) and perform it inside _persist_telemetry only after the `plug.gateway_id != gateway_id` check passes (telemetry.py:409+), so the store is only ever fed for a plug the publishing gateway actually owns. If keeping the update on the paho thread for latency is required, gate it on an in-memory plug_id->gateway_id ownership map refreshed from the roster/DB and reject a mismatch. Defense-in-depth: make finalize_charging_session bill only from the guarded persisted `session.energy_kwh` (which is updated every frame by the ownership-checked path) rather than max(live, persisted) from the mutable store, removing the store as a billing sink entirely.

### 3. [MEDIUM] Per-IP rate limiter trusts leftmost X-Forwarded-For entry — spoofable, bypasses login/register/forgot-password/API-floor limits

- **Location:** `backend/services/rate_limit.py:108`  
- **Surface / category:** auth / auth-rate-limit-bypass  
- **What:** client_ip() returns fwd.split(",")[0].strip() — the LEFTMOST X-Forwarded-For token. In a proxy chain the leftmost entry is the client-supplied/spoofable end; every honest proxy APPENDS on the right. The frontend nginx uses `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` (frontend/nginx.conf:20), which preserves the client-originated portion and only appends its own peer, and the generated Caddyfile (deploy/relay/deploy-relay.sh:250-262) sets NO `trusted_proxies` and no header sanitization (image `caddy:2-alpine`, a floating tag). So the leftmost value the backend keys its per-IP limiters on is attacker-influenced. The code comment at rate_limit.py:101-106 itself concedes the header is 'client-forgeable' in the -NoTls rollback stack. This key feeds every per-IP limiter: login (per-IP), register (10/hr), forgot-password (5/hr), reset-password, public-map, and the blanket 300/min API DoS floor (api_rate_limit_middleware). Per-ACCOUNT limiters (login-by-email, session/payment/etc.) key on normalized email / user.id and are NOT affected.  
- **Exploit:** An unauthenticated attacker sends POST /api/auth/forgot-password for a specific victim email repeatedly, rotating a forged `X-Forwarded-For: <random-ip>` header on each request. Because the per-IP forgot-password limiter (5/hour) is keyed on the spoofed leftmost value, each fake IP gets a fresh budget, turning the endpoint into an unbounded reset-email mailbomb against the victim's inbox. The same trick gives unbounded /register account-existence probing / bulk signup and defeats the 300/min per-IP API DoS floor. This is definitely live in the documented -NoTls rollback stack; in the Caddy-TLS stack exploitability depends on Caddy's default XFF handling, which is not hardened here.  
- **Fix:** Do not trust the leftmost XFF entry. Configure Caddy with `trusted_proxies` (the compose network's private ranges) so it emits a trustworthy client IP, and in client_ip() select the client IP by a FIXED offset from the RIGHT of the chain based on the known number of trusted hops (client -> Caddy -> nginx = 2), or read a single dedicated header that only the trusted front proxy is allowed to set. Reject/ignore any client-supplied XFF beyond the trusted-hop count.

### 5. [MEDIUM] Login CSRF / session fixation: OAuth callback consumes an unbound bearer JWT from the URL fragment

- **Location:** `frontend/src/pages/GoogleCallback.jsx:54`  
- **Surface / category:** web / auth-csrf  
- **What:** The Google sign-in callback lands on /auth/google/callback#token=<JWT>. GoogleCallback reads the token straight out of window.location.hash (lines 37-38) and hands it to AuthContext.loginWithToken(), which unconditionally writes it to localStorage and adopts it as the active session (AuthContext.jsx line 84), then calls refreshUser(). There is NO binding between this final token and the browser session that initiated the OAuth flow: no state/nonce cookie is checked on the SPA side, and the code comment explicitly notes the JWT 'is fine to reuse' (i.e. not single-use). Any valid server-issued JWT dropped into the fragment is accepted. Because it is a bearer token, whoever's token is planted becomes the logged-in identity for that browser. There is also no 'you are already signed in' guard before the session is replaced.  
- **Exploit:** An attacker registers/logs in to their own AmpHive account and captures their own valid JWT. They craft https://amphive.app/auth/google/callback#token=<ATTACKER_JWT> and send it to a victim (email, QR, chat). The victim clicks; GoogleCallback silently stores the attacker's token and navigates to '/'. The victim is now operating inside the attacker's account. If the victim then opens Wallet and adds charging credit with their own card, the create-order/verify calls carry the attacker's token, so the money credits the attacker's balance (Wallet.jsx handlePay). Alternatively the victim enters PII or starts sessions that are recorded against the attacker's account, or is set up for a convincing phishing state. This is classic login-CSRF; it requires victim interaction and that they not notice the wrong account, hence medium.  
- **Fix:** Bind the OAuth result to the initiating browser: end the server-side OAuth flow by setting the app session as an httpOnly, Secure, SameSite=Lax cookie instead of returning a bearer JWT in the fragment; OR return a short-lived, single-use, session-bound code that the SPA exchanges via POST while validating a nonce cookie that was set when the flow started. At minimum, make the fragment token single-use with a very short TTL bound to a state nonce, and in loginWithToken refuse to silently replace an existing authenticated session without explicit user confirmation.

### 8. [LOW] Lock-order inversion: PATCH session-limits (user→session) vs finalize (session→user) can deadlock

- **Location:** `backend/routers/sessions.py:430`  
- **Surface / category:** money / concurrency-race  
- **What:** update_session_limits() acquires the User row lock first (backend/routers/sessions.py:430, `select(User)...with_for_update()`) and then the ChargingSession row lock (sessions.py:436). finalize_charging_session() acquires them in the OPPOSITE order: the ChargingSession row lock first (backend/services/session_lifecycle.py:155) and then the User row lock via debit_wallet_clamped() (session_lifecycle.py:247 -> backend/services/wallet.py:62). For the same (user, session) pair this is a classic AB-BA lock cycle. The in-code comment in update_session_limits' docstring (sessions.py ~406-408: "user -> session order here has no cycle with finalize's session -> user") asserts the opposite of what the code does — user→session and session→user ARE a cycle. Both endpoints operate only on ACTIVE sessions, so the pair genuinely overlaps at runtime. IMPORTANT calibration: this is NOT a money bug. Postgres' deadlock detector aborts exactly one transaction (SQLSTATE 40P01) and rolls it back atomically — no double-spend, no lost/created coins, no torn state. It is a transient-availability/robustness defect only.

However, live verification against the production VM (136.117.94.209, resolved from amphive.app) on 2026-08-04 disproves the finding's central claim of current exposure: (1) http://136.117.94.209/ returns 308 Permanent Redirect to https://136.117.94.209/ from Caddy, serving zero app content; (2) a spoofed unknown Host (Host: evil.example.com) on :80 also returns 308 to https://{host}/ — the live Caddyfile implements exactly the `redir https://{host}{uri} permanent` remediation the finding itself recommends; (3) HTTPS on the bare IP fails the TLS handshake entirely (no cert for the IP), so the app is unreachable via the IP in any form; (4) http://amphive.app returns 308 to https://amphive.app. The script generates its weak starter Caddyfile only when none exists (line 233) and explicitly preserves the existing file on every subsequent run (line 273), and the operator-edited production Caddyfile has been hardened past the repo version. No user can therefore conduct a login or transmit a JWT in plaintext to this server, so the described MITM capture scenario has no reachable path. What survives is repo-vs-prod drift: a from-scratch disaster-recovery rebuild (or deleting the Caddyfile to regenerate, as the file header invites) would reintroduce the plaintext-serving window until the manual hardening edit is repeated, and the Caddyfile.example justification ("tighten to a redir once a paid/reliable domain is in place") is stale since amphive.app went live 2026-07-20. That is an insecure-default/hygiene issue in deploy tooling — worth fixing by making the generated block emit the redirect — but not a reachable vulnerability today, hence FALSE_POSITIVE at info severity rather than the reported low.
- **Session JWT stored in localStorage (readable by any in-origin JavaScript, incl. allowed third-party script)** (`frontend/src/api/client.js:35`) — Every factual claim in the finding is accurate — the JWT is in localStorage (client.js:35, AuthContext.jsx:64/84/106, SessionContext.jsx:83), it is the sole bearer credential, and the CSP (deploy-relay.sh:240) both allows https://*.razorpay.com in script-src and leaves img-src/connect-src open to arbitrary https: for exfil. Razorpay checkout.js IS injected into the top-level origin (utils/razorpay.js appends a <script> to document.head), not a sandboxed iframe. So the write-up is honest and correctly scoped.

But this is not a presently-exploitable vulnerability, and the finding admits as much: the exploit is entirely contingent on a precondition that does not exist in the current code or is outside the attacker's control. I verified reachability end-to-end and it is BLOCKED:

1) No first-party XSS. Grep for dangerouslySetInnerHTML|innerHTML|outerHTML|insertAdjacentHTML|eval(|new Function|document.write across frontend/src returns ZERO matches. React auto-escapes JSX; safePath.js explicitly rejects javascript: and open-redirect targets. The only backend HTML surface, render_invoice_html (services/invoices.py), html.escape()s every user-controlled field (driver name/email, tenant legal_name/GSTIN, invoice_number) and interpolates only numerics otherwise.

2) Strong CSP actively resists injection. script-src is 'self' https://*.razorpay.com with NO unsafe-inline and NO unsafe-eval, so even a hypothetical injected inline <script>/handler or eval payload cannot run; an attacker cannot host script on 'self' or on *.razorpay.com. The open img-src/connect-src exfil channels only matter AFTER a script already executes, which is the step that is blocked.

3) The Razorpay angle is a real trust dependency but not attacker-reachable: it requires compromising a Tier-1 payment provider (or a *.razorpay.com host) — outside the attacker's control and outside this repo — and it is the vendor-recommended integration model used by essentially every Razorpay/Stripe merchant. It is now also loaded on-demand only on the Wallet page (index.html has no global preload), narrowing exposure.

Per the review rule ("FALSE_POSITIVE unless you can articulate a concrete, reachable exploit path with no mitigating control in the way"), I cannot articulate such a path — the mitigating controls are all in the way. This is a legitimate defense-in-depth hardening recommendation, not a bug an attacker can reach today. I downgrade low -> info because there is no exploitable condition absent an external/future precondition. I also note the recommended httpOnly-cookie fix is only a partial mitigation: a compromised in-origin script could still ride a same-origin cookie to perform authenticated actions even if it cannot read the raw token — reinforcing that this is a hardening nuance rather than a clean vuln. Nothing here escalates severity: no XSS sink, no unsafe-inline/eval, no unescaped HTML sink.
- **Setup code (WPA2 passphrase + provisioning token) generated via esp_random() before the RF subsystem is started on first boot** (`firmware/main/main.c:467`) — The code-ordering claim is factually correct: on first boot config_loaded is false, so wifi_init() returns at main.c:1014-1016 before esp_wifi_start() (line 1024); start_captive_portal() then generates the setup code via esp_random() (main.c:467) before esp_wifi_start() at line 949, and only esp_wifi_init() (driver init, no RF/PHY power-up) has run. However, the security conclusion — that the code is therefore predictable — is refuted by the boot-entropy design of the exact platform in use, verified in the ESP-IDF v5.3.3 source tree on this machine (the version in firmware/sdkconfig, CONFIG_IDF_INIT_VERSION="5.3.3"). (1) The default second-stage bootloader unconditionally enables the SAR-ADC thermal-noise entropy source at boot start (bootloader_esp32.c:240, bootloader_esp32c3.c:190 -> bootloader_init.c:96-100) and disables it only immediately before jumping to the app (bootloader_utility.c:693-694), so the entire bootloader run (flash init, partition load, app-image SHA verification) mixes physical noise into the WDEV RNG state. (2) bootloader_random_disable() (bootloader_random_esp32.c:78-120) tears down only the I2S/SAR-ADC plumbing and does not reset the RNG state, so the entropy seeded milliseconds earlier in the same boot is still in the generator when app_main draws the 10 words. (3) Espressif's own docs for this exact version say the bootloader source "provides entropy for any first boot key generation" and "seeds the internal RNG state with some entropy" (docs/en/api-reference/system/random.rst:26,49) — the first-boot setup code is precisely such a first-boot generation; the "pseudo-random only" caveat is about sustained streams, not the predictability of ~50 bits drawn right after a noise-seeded boot. (4) On ESP32-C3 (the chip the fleet actually runs per the repo's docs refresh), random.rst:55-60 documents a secondary always-on entropy source (async 8 MHz oscillator sampling) continuously mixed into the RNG state by hardware, which alone passed Dieharder across continuous resets. The entire exploit chain hinges on predicting the RNG output; no published attack predicts esp_random() output in an app launched by the standard IDF bootloader (known Espressif RNG weaknesses concern ESP8266 or setups where no entropy source was ever enabled since power-on). Without prediction the attacker faces a ~49.5-bit code (10 chars over a 31-symbol alphabet) as a WPA2-PSK (offline crack needs the installer's handshake plus a PBKDF2-hardened ~2^48.5 search) and a /save token whose online guessing is bounded by the 10-minute portal idle reboot — plus mandatory physical RF presence during the one-time first-boot provisioning window. No concrete, reachable exploit path exists with these controls in the way. What survives is a legitimate defense-in-depth note (Espressif recommends an active entropy source at generation time); the one-line fix — generate the code after esp_wifi_start(), or bracket the loop with bootloader_random_enable()/bootloader_random_disable() — is cheap hygiene worth doing, hence info rather than dismissal without remark.
